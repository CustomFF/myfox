# MyFox: переход автоматизации на Python — ТЗ и план

Статус: архитектура согласована (ветка `installer-rethink`), реализация не начата.
Этот документ заменяет `docs/refactor-plan.md` для части «установщик» — тот план
предполагал причёсывание существующего bash, этот — замену на Python с нуля.
Твики браузера (`autoconfig/`, `chrome/`, `assets/`, `themes/`) не переписываются
и этим планом не затрагиваются.

## Принципы

- Python 3.8+ как нижняя планка совместимости.
- Стандартная библиотека — основной инструмент. Сторонние зависимости — только
  вендором (исходники в репозитории) для чистого Python, или собственным
  релизом-как-хостингом (без PyPI в рантейме) для бинарных.
- Никакого venv/pip нигде в проекте, ни у конечного пользователя, ни в
  рантайме GUI-пути.
- Bash остаётся только в одной точке: `get.sh`, несколько строк, скачивает и
  запускает `bootstrap.py`.
- Комментарии: факт вперёд, контекст после. Без «единственный вход в двух
  ролях»-подобных заходов (см. пример-эталон в переписке от 30.09).
- Порядок работы — «прогрессивный JPEG»: сначала весь каркас целиком (пусть
  местами бутафорский), потом резкость по частям. Не доводить один модуль до
  идеала, пока остальные не существуют даже в черновом виде.

## Отклонённые варианты (зафиксировано, чтобы не возвращаться)

| Вариант | Почему отклонён |
|---|---|
| Компилируемый бинарник (Go и т.п.) как ядро | пользователь принципиально против непрозрачного бинарника как механизма автоматизации |
| `tkinter` для GUI | внешний вид |
| `PySide6`/Qt для GUI | 93 МБ, **wheel под linux arm64 не существует на PyPI вообще** |
| `PyGObject`/GTK для GUI | на PyPI нет прекомпилированных wheel, только sdist; сборка требует системный C-тулчейн + dev-заголовки GTK |
| `zenity`/`kdialog` вместо dialog/whiptail | та же природа риска, что у dialog/whiptail — «обычно стоит», не гарантия |
| venv+pip для основного (не-GUI) пути | реинкарнация той же проблемы «а точно ли установится», которую и решаем |
| Вендорить `dearpygui` в git | это не портируемые исходники — `_dearpygui.so` собран под конкретную пару (минорная версия CPython × архитектура), ~9.3 МБ каждая; вендор «на все версии» — от 100 МБ |
| Показывать несовпадение версии твиков и установленного Firefox | продуктовая логика: тестируем на бете, бета становится стабильной без изменения кода — разъезда по факту не бывает; Nightly — не наша забота |
| `myfox install` как явная команда | бессмысленна: единственный путь попасть в мастер — через bootstrap, когда MyFox ещё не стоит |
| `refresh --full` (перепроверка браузера через refresh) | снято, когда развели `refresh` (только твики) и `reinstall` (только браузер) — им незачем пересекаться |

## Декомпозиция

### 1. Слой доставки (вне пакета `myfox/`)
- **`get.sh`** — POSIX sh, несколько строк: `curl` бутстрап, `exec python3 -c "$(...)" "$@"`.
- **`bootstrap.py`** — без версии (качается заново при каждом вызове, поэтому
  всегда «последний»). Смотрит state офлайн: установлено — зовёт локальный
  `~/.local/share/myfox/__main__.py` напрямую; не установлено — качает core-архив
  и передаёт ему управление (это и запускает мастер, отдельной команды `install`
  для этого нет).

### 2. Ядро — `myfox/` (свой версионный трек, тег `core-*`)
- `__main__.py` — argparse, диспетчер: `browser|refresh|reinstall|uninstall|help`.
- `state.py` — json-состояние (замена awk key=value).
- `i18n.py` + `locales/{en,ru}.json`.
- `version.py` — сверка тегов с GitHub Releases API (`releases/latest` на оба трека
  независимо — `core-*` и твик-тег), без скачивания архива ради проверки.
- `firefox.py` — тарбол, определение языка/архитектуры, генерация `.desktop`
  и `firefox-myfox`-обёртки (перенос `lib/firefox.sh` — это предметная логика
  Mozilla/freedesktop, а не «баш-налог», меняется мало).
- `profiles.py` — `profiles.ini`/`installs.ini` через `configparser` вместо
  ручного awk-парсера; headless-пиннинг инсталла (перенос `lib/profile.sh` —
  тоже предметная логика, не упрощается переходом на другой язык, просто
  читается человеком).
- `apply.py` — копирование `autoconfig/`/`chrome/`/букмарклетов в профиль.
- `addons.py` — установка тем (уже свои, подписанные — просто копирование
  файла) и Plasma-интеграции (AMO-логика, `urllib` вместо `curl`+awk).
- `wizard.py` — явный стек экранов (список пройденных шагов + текущий),
  не строка-состояние с кодами возврата 0/1/3.

### 3. UI-слой — `myfox/ui/`
Один интерфейс (`confirm`, `choose`, `input_dir`, `spinner`, `message`), три реализации:
- `plain_backend.py` — `input()`, без сторонних зависимостей. Реализуется первым
  (тривиален), даёт рабочий сквозной путь на первом же проходе.
- `urwid_backend.py` — поверх вендоренного `_vendor/urwid`. Сам управляет
  alt-screen, без ручного terminfo-патчинга.
- `dearpygui_backend.py` — поверх `_vendor_fetch.py` (см. ниже), только когда
  нет tty и есть `$DISPLAY`/`$WAYLAND_DISPLAY`, либо явный `--gui`.
- Выбор бэкенда — в `ui/__init__.py`, по автоопределению + `--gui`-override.

### 4. Вендор и загрузка бинарных зависимостей
- `_vendor/urwid/`, `_vendor/wcwidth/` — исходники в git, ставятся сейчас же,
  один раз, руками (см. проверку от 30.09 — LGPL-2.1 и MIT, чистый Python).
- `_vendor_fetch.py` — для `dearpygui`: качает нужную пару (версия Python ×
  архитектура) **с нашего же GitHub Release** (не PyPI), кладёт в
  `~/.local/share/myfox/.dearpygui-cache/`, добавляет в `sys.path`. Собранные
  пары — 3.10–3.13 × amd64/arm64, готовятся и заливаются в релиз заранее,
  руками, не автоматикой GHA.

### 5. Инфраструктура релизов
- Два независимых тега/потока: `core-*` (автоматизация) и `<beta-major>.<патч>`
  (твики) — тег ставится вручную, GHA реагирует на паттерн, собирает свой
  архив, публикует релиз. Один пуш тега — один релиз одного трека.
- `scripts/build-core-dist.sh` — упаковывает `myfox/` (+ `_vendor/`).
- `scripts/build-tweaks-dist.sh` — упаковывает `autoconfig/`+`chrome/`+`assets/`+`themes/`.
- `Makefile` — `make install|uninstall|refresh|reinstall` из рабочей копии,
  напрямую `python3 -m myfox <команда>`, без сборки архивов (это только для
  реального релиза).

## Семантика команд (зафиксировано)

- `myfox browser [аргументы]`
- `myfox refresh` — трек твиков: тег ≠ state → качает и применяет только
  `autoconfig/chrome/assets/themes`, предлагает перезапуск браузера. Трек
  автоматизации: тег ≠ state → качает и заменяет `~/.local/share/myfox`
  целиком, без хотсвопа («при следующем запуске»). Ничего не изменилось
  нигде — одна строка «всё свежее».
- `myfox refresh --force` — оба трека безусловно, без сверки тегов.
- `myfox reinstall` — только браузер, безусловно; твики переналивает из уже
  лежащего локально пакета, в сеть за ними не ходит.
- `myfox uninstall`, `myfox help` — как сегодня по смыслу.
- `-y` — везде отключает вопросы. `--gui` — форсирует GUI-бэкенд там, где
  бэкенд вообще участвует.

## План по проходам («прогрессивный JPEG»)

Каждый проход — рабочее состояние всей системы целиком, не одного модуля.
Проверка после каждого прохода — как обычно: песочница
(аналог `scratch/sandbox.sh`, переменные окружения вместо реального `$HOME`),
сначала бета, потом стабильная версия.

**Проход 1 — Скелет.**
Структура каталогов, `__main__.py` с argparse на все команды, `state.py`
(json), `i18n.py` + минимальный набор строк, `ui/plain_backend.py`,
`ui/__init__.py` с интерфейсом. Всё остальное — заглушки/явные `TODO`.
Критерий готовности: `python3 -m myfox --help` и `python3 -m myfox refresh`
(на пустом состоянии) отрабатывают до конца, ничего не падает, вывод честно
говорит «пока не реализовано» там, где заглушка.

**Проход 2 — Реальная логика, без полировки UI.**
`firefox.py` (скачивание/распаковка тарбола, язык/архитектура, `.desktop`),
`profiles.py` (реальный `configparser`, headless-пиннинг), `apply.py`,
`addons.py`, `version.py` с реальным обращением к GitHub Releases API.
Всё ещё через `plain_backend`. Критерий готовности: установка/`refresh`/
`uninstall` реально работают end-to-end, функционально не хуже текущего
bash-инструмента, просто без красивого интерфейса.

**Проход 3 — Терминальный UI.**
Вендорим `urwid`+`wcwidth`, пишем `urwid_backend.py`, `wizard.py` (стек
экранов: welcome → путь → канал → язык → профиль → твики → тема → сводка,
с «Назад»). Критерий: интерактивный запуск в терминале выглядит и ведётся
не хуже нынешнего dialog-мастера.

**Проход 4 — GUI-путь.**
Собираем и заливаем на релиз пары `dearpygui` (3.10–3.13 × amd64/arm64),
`_vendor_fetch.py`, `dearpygui_backend.py`, `--gui`, пункт контекстного меню
в `.desktop`. Критерий: клик по пункту меню открывает диалог, не консоль.

**Проход 5 — Самообновление и дистрибуция.**
Два трека версий в `refresh` по-настоящему (не заглушка), `bootstrap.py`
реальный, `scripts/build-{core,tweaks}-dist.sh`, GHA на оба тега. Критерий:
`myfox refresh` на реально устаревшей локальной копии докатывает свежее,
`curl | bash` работает с реального (или локально поднятого) релиза от начала
до конца.

**Проход 6 — Полировка.**
Ревизия всех текстов (никакого «обновляю твики (как myfox update)» —
конкретный, контекстный текст под каждый исход), ревизия комментариев по
эталону, граничные случаи, `README`/`AGENTS.md` под новую архитектуру
(здесь же — давно отложенная переработка `README`, см. память).

## Соответствие старому коду (чтобы не потерять функциональность)

| Было (bash) | Стало (Python) |
|---|---|
| `lib/common.sh` (state, opts, цвета, пути) | `state.py` + `ui/` (цвета — забота бэкенда, не общего кода) |
| `lib/i18n.sh` + `i18n/*.sh` | `i18n.py` + `locales/*.json` |
| `lib/tui.sh` | `ui/` (три бэкенда) |
| `lib/firefox.sh` | `firefox.py` |
| `lib/profile.sh` | `profiles.py` |
| `lib/apply.sh` | `apply.py` |
| `lib/addons.sh` | `addons.py` |
| `bin/myfox-core` (парсинг флагов) | `argparse` в `__main__.py` |
| `bin/myfox-core` (`install_wizard`/`_uninstall_wizard`) | `wizard.py` (стек экранов) |
| `get.sh` | `get.sh` (сильно короче) + `bootstrap.py` |
| `scripts/build-dist.sh` | `scripts/build-{core,tweaks}-dist.sh` |
| `scripts/dev-serve.sh` | не нужен так же: `Makefile` дёргает `python3 -m myfox` из рабочей копии напрямую |
| `scripts/{build,sign}-themes.sh` | без изменений, не относятся к этому плану |
